技术点地图

先知道每个技术为什么出现在简历里，再去背问题。

LangGraph

技术点

把复杂 LLM 流程组织成状态图，适合多 Agent、条件分支、人工复核和异常回退。

项目里的作用
在导诊项目里用于分诊路由、症状问询、RAG、报告解读、医生复核等节点编排。
为什么选它
比普通链式调用更可控，能把状态、条件边和中断逻辑显式写出来。
类似技术
Dify Workflow、Coze Workflow、AutoGen、CrewAI、Semantic Kernel、普通规则引擎。
面试风险
必须讲清 State 字段、节点职责、条件边，不要只说“用了多 Agent”。

LangChain

技术点

大模型应用开发框架，常用于组织 Prompt、Retriever、模型调用、输出解析。

项目里的作用
在 RAG 项目中辅助串起检索上下文、提示词、模型回答和结构化输出。
为什么选它
生态成熟，接 Retriever、PromptTemplate、LLM 调用比较方便。
类似技术
LlamaIndex、Haystack、RAGFlow、Dify。
面试风险
不要把 LangChain 讲成核心能力，真正核心是数据、召回、重排、评测和安全边界。

RAG

技术点

检索增强生成，先从知识库找证据，再让大模型基于证据回答。

项目里的作用
用于疾病科普、药品说明、急救知识、科室 FAQ 等医疗问答场景。
为什么选它
可更新、可溯源，比单纯微调更适合业务资料持续变化的场景。
类似技术
微调、知识图谱问答、搜索引擎问答、Long Context。
面试风险
医疗场景不能说“检索不到也让模型回答”，必须有拒答或人工复核。

FAQ 快速命中

技术点

对高频标准问题优先返回确定答案，避免每次走完整 RAG 和大模型生成。

项目里的作用
挂号科室、检查注意事项、常见药品用法、急救提示等标准问答。
为什么选它
快、稳定、成本低，也更容易保证答案一致性。
类似技术
意图分类、关键词模板、ES 检索、Redis 缓存。
面试风险
要说明命中不可靠时会回退 RAG，不是强行返回 FAQ。

BM25

技术点

经典关键词检索算法，基于词频、逆文档频率和文档长度归一化排序。

项目里的作用
补充药品名、指标名、科室名、检查项等精确词召回。
为什么选它
对专有名词和短词命中稳定，能弥补向量召回对精确词不敏感的问题。
类似技术
TF-IDF、Lucene、Elasticsearch、OpenSearch。
面试风险
不要说 BM25 理解语义，它主要解决关键词匹配。

BGE-M3 / Embedding

技术点

把文本转成向量，用语义相似度做召回。

项目里的作用
处理用户自然语言描述，比如“胸口闷、喘不上气该挂什么科”。
为什么选它
中文检索效果和社区成熟度较好，也支持多粒度检索思路。
类似技术
bge-large-zh、m3e、E5、text-embedding 系列。
面试风险
要说明向量只是初召回，不等于最终答案，还需要重排和安全约束。

Milvus

技术点

向量数据库，用于存储 embedding 并进行相似度检索。

项目里的作用
保存知识块向量，按用户问题召回相似医学资料片段。
为什么选它
比自己写 FAISS 服务更工程化，支持集合、索引、过滤和扩展。
类似技术
FAISS、Qdrant、Weaviate、pgvector、Elasticsearch dense_vector。
面试风险
别说 Milvus 是存原文的普通数据库，原文和元数据通常还会在关系库或文件系统中管理。

BGE-Reranker

技术点

重排模型，对 query 和候选片段做更精细的相关性判断。

项目里的作用
对 BM25 和向量召回的候选片段重新排序，选出最适合生成答案的上下文。
为什么选它
Cross-Encoder 同时看问题和片段，比单纯向量相似度更准。
类似技术
Cohere Rerank、m3e-reranker、ColBERT、LLM rerank。
面试风险
会增加耗时，要能解释 rerank_k 和 P95 的取舍。

父子分块

技术点

小块用于精准召回，大块用于补充上下文。

项目里的作用
处理药品说明书、疾病资料、急救知识时保留标题层级和上下文。
为什么选它
避免固定长度切分把禁忌、适应症、注意事项切散。
类似技术
递归分块、Markdown 标题切分、语义分块、滑动窗口。
面试风险
要能说明父块、子块分别存什么，引用展示和生成上下文用哪个粒度。

Hybrid Search

技术点

混合召回，把关键词召回和向量召回结合起来。

项目里的作用
医疗问答里既有药名指标这种精确词，也有患者自然语言症状描述。
为什么选它
BM25 管精确词，向量管语义表达，重排模型做最终筛选。
类似技术
RRF、加权融合、候选合并 + rerank、ES hybrid search。
面试风险
如果没做复杂融合公式，就说候选合并后交给 reranker，不要装算法专家。

Prompt Engineering

技术点

把任务说明、上下文、输出格式、安全规则组织成提示词。

项目里的作用
约束医疗回答只做科普、引用证据、提示风险，不输出诊断结论。
为什么选它
能统一输出结构，减少无来源回答和越界表达。
类似技术
Guardrails、函数调用、JSON Schema、内容审核模型、规则引擎。
面试风险
不能说只靠 Prompt 保证安全，必须配合规则、拒答和人工复核。

HitL 人工复核

技术点

Human in the Loop，人参与关键结果确认。

项目里的作用
医生对 AI 生成的导诊建议、报告解读和接诊摘要进行确认或修正。
为什么选它
医疗场景高风险，AI 只能辅助，正式意见要人工兜底。
类似技术
审批流、审核队列、客服转人工、LangGraph interrupt。
面试风险
初级开发建议说“实现待复核状态和页面展示”，不要说自己定义合规制度。

TypedDict + Pydantic

技术点

TypedDict 描述状态字段，Pydantic 做数据校验和结构化解析。

项目里的作用
管理患者基础信息、症状、病史、风险标记、科室建议、报告异常项等字段。
为什么选它
降低多节点之间字段混乱和 LLM 输出格式不稳定的问题。
类似技术
dataclass、Marshmallow、JSON Schema、TypeScript interface。
面试风险
要能说校验失败怎么办，比如补充追问、默认值、错误返回。

asyncio.gather

技术点

Python 异步并发工具，用于同时执行多个互不依赖的任务。

项目里的作用
报告指标解读、多个质控维度评审可以并行处理。
为什么选它
LLM/API 调用多为 IO 等待，并行后总耗时接近最慢任务，而不是所有任务相加。
类似技术
线程池、进程池、Celery、消息队列、并行 Agent 节点。
面试风险
要说明超时、异常隔离和部分失败兜底。

FastAPI

技术点

Python Web 框架，用于封装 API 服务。

项目里的作用
提供问答、检索结果、反馈记录、复核状态、报告解读等接口。
为什么选它
异步支持好，和 Pydantic 结合紧密，接口文档自动生成。
类似技术
Flask、Django REST Framework、Sanic、Tornado。
面试风险
要能讲接口字段、异常返回、日志记录，不要只说“写接口”。

MySQL / PostgreSQL

技术点

关系型数据库，保存结构化业务数据。

项目里的作用
存 FAQ、用户反馈、医生复核状态、引用元信息、评测记录等。
为什么选它
事务稳定，查询和统计方便，业务团队容易维护。
类似技术
SQLite、MongoDB、Elasticsearch、ClickHouse。
面试风险
如果说 PostgreSQL，要准备 JSONB、索引、事务等基础追问。

Redis

技术点

内存数据库，常用于缓存和临时状态。

项目里的作用
FAQ 热点缓存、会话状态、临时任务结果、接口响应缓存。
为什么选它
读写快，能降低重复查询和响应延迟。
类似技术
Memcached、本地 LRU、数据库缓存表。
面试风险
要能说 TTL、缓存失效和数据一致性。

React + TypeScript + Ant Design

技术点

前端开发组合，用于构建业务页面和交互。

项目里的作用
展示问答结果、引用来源、风险提示、加载状态、医生复核状态、异常反馈。
为什么选它
React 组件化，TS 约束字段，AntD 适合后台/业务系统快速交付。
类似技术
Vue + Element Plus、Arco Design、Naive UI、Next.js。
面试风险
要能讲清楚如何展示引用、错误态、流式返回和复核状态。

PyMuPDF

技术点

PDF 解析库，可抽取文本、页码和基础布局信息。

项目里的作用
解析医学资料 PDF 或体检报告文本。
为什么选它
速度快，适合文本型 PDF 的抽取。
类似技术
pdfplumber、pypdf、PaddleOCR、Tesseract。
面试风险
扫描件要 OCR，不能说 PyMuPDF 能解决所有报告识别。

Evaluation / Recall@5 / P95

技术点

用指标评估检索、回答、安全和性能。

项目里的作用
评估 Top5 召回率、引用命中率、拒答准确性、P95 耗时和 bad case。
为什么选它
比“感觉效果变好”更可信，也方便持续优化。
类似技术
RAGAS、DeepEval、TruLens、人工评测表。
面试风险
必须说清楚开发测试口径、样本量和计算方式。

完整问题库

每题都有口语化答案、知识点解释、追问和避坑。
01 开场与简历真实性 你先简单介绍一下你自己，以及你现在主要做什么方向？
口语化回答

我主要做 AI 应用开发，重点在医疗 RAG 和 Agent Workflow 这块。我的优势不是底层模型训练，而是把大模型能力接到业务流程里，比如资料清洗、检索召回、重排、接口封装、前端展示、风险提示和人工复核状态流转。简单说，我更偏应用落地和工程链路。

相关知识点解释

这题是定人设。你要把自己定位成“AI 应用开发”，不要说成“算法专家”或“架构负责人”。

可能继续追问

面试官会继续问：那你最熟的是 RAG 还是 Agent？建议回答：RAG 链路更熟，Agent 是在业务编排里做过部分节点实现。

不要这么答

不要上来就说“我精通大模型全链路”。一年经验扛不住。

02 开场与简历真实性 你一年左右经验，为什么简历上技术栈这么多？哪些是你真正做过的？
口语化回答

这里我会分层说。真正上手比较多的是 Python、FastAPI、React、RAG 数据处理、BM25/向量召回接入、Reranker 调参、接口联调和页面展示。LangGraph、多 Agent 和医疗安全规则是项目里参与实现过部分节点，但整体方案不是我一个人定的。像模型训练、合规方案这类我不会说自己负责，只是了解和配合。

相关知识点解释

把“熟悉/了解/参与/负责”分清楚，是降低真实性风险的关键。

可能继续追问

如果面试官让你选最能深挖的点，就选 RAG 检索链路和问诊状态机。

不要这么答

不要说所有技术都很熟，面试官会逐个击破。

03 项目边界 你这两个项目是不是一个项目拆成两个写？
口语化回答

不是简单拆分。医疗知识库 RAG 问答系统更像底座，解决资料清洗、FAQ、混合召回、重排、引用来源和安全拒答。多 Agent 项目是上层业务流程，把分诊路由、问诊状态机、报告解读、医生复核串起来，其中医学指南 RAG Agent 会调用知识库能力。所以一个偏知识检索，一个偏业务编排。

相关知识点解释

RAG 是能力底座，多 Agent 是流程编排。这个边界必须背熟。

可能继续追问

如果问两个项目是否共用服务，可以说：可以共用知识库检索服务，但业务入口和状态流转不同。

不要这么答

不要说“两个项目完全没关系”，因为简历里确实有 RAG 交叉。

04 项目边界 这两个项目里，你个人最核心的贡献是什么？
口语化回答

RAG 项目里，我主要做资料清洗、父子分块、元数据整理、检索参数调优、接口返回结构和前端引用展示。多 Agent 项目里，我更偏问诊状态结构、危急词规则接入、报告指标并行解读、待复核状态流转和前后端联调。整体架构和医疗业务规则是团队一起定的。

相关知识点解释

用“我负责的模块”回答，不要讲整个系统都是自己做的。

可能继续追问

可以准备一个具体例子：某个 bad case 如何从召回错定位到分块或 metadata 问题。

不要这么答

不要把团队成果全部揽到自己身上。

05 多 Agent / LangGraph 什么是 Agent？你项目里的 Agent 是真正自主智能体吗？
口语化回答

我项目里的 Agent 更准确说是带明确职责的工作流节点，不是完全自主规划的智能体。比如分诊路由 Agent 做科室和风险判断，症状问询 Agent 做缺失字段追问，RAG Agent 做知识检索，报告解读 Agent 做指标解释。它们不是随便自己决定做什么，而是在 LangGraph 流程里按状态和条件边执行。

相关知识点解释

很多面试官反感把普通节点硬叫 Agent。你主动承认是 Workflow Agent，会更可信。

可能继续追问

如果问自主 Agent 和 Workflow Agent 区别：自主 Agent 偏规划和工具选择，Workflow Agent 偏固定流程和可控编排。

不要这么答

不要说“Agent 可以自己思考并完成所有导诊”。

06 多 Agent / LangGraph LangGraph 相比 LangChain 普通 Chain 有什么优势？
口语化回答

普通 Chain 更像线性流程，适合一步一步执行。LangGraph 更像状态图，可以定义多个节点、条件边、循环、中断和人工复核。医疗导诊不是简单问答，中间可能出现危急症状直接中断，也可能字段缺失要回到追问，所以用图结构更合适。

相关知识点解释

关键词：状态图、条件边、中断、循环、人工复核。

可能继续追问

面试官可能问 conditional edge 怎么用，你可以说根据 risk_flags、missing_fields、review_status 决定下一节点。

不要这么答

不要只说“LangGraph 更高级”。

07 多 Agent / LangGraph 你们 LangGraph 的 State 里都放了什么字段？
口语化回答

我会把 State 分成几类：患者基础信息，比如年龄、性别；问诊信息，比如主诉、症状、持续时间、伴随症状、既往史、过敏史、用药史；流程字段，比如 missing_fields、risk_flags、current_stage；结果字段，比如 department_suggestion、rag_context、report_abnormal_items、summary、review_status。这样每个节点只更新自己负责的字段。

相关知识点解释

State 是 Agent 编排的核心。能说出字段，就比泛泛讲 Agent 更可信。

可能继续追问

如果问为什么不用普通 dict：TypedDict/Pydantic 能约束字段，减少格式错误。

不要这么答

不要回答“就是存用户输入和模型输出”。太浅。

08 多 Agent / LangGraph 节点之间怎么流转？条件边怎么判断？
口语化回答

入口先走安全规则和分诊路由，如果 risk_flags 命中高危，就直接进入急诊提示或人工处理；如果非高危，就进入症状问询。问询节点会检查 missing_fields，如果还有缺失就继续追问，如果信息够了再进入 RAG 或报告解读。最后生成的摘要和建议进入 review_status=pending，等医生复核。

相关知识点解释

回答要体现“安全前置”和“状态驱动”，而不是模型自由发挥。

可能继续追问

如果问条件边字段，可以说 risk_flags、missing_fields、has_report、review_status。

不要这么答

不要说“让模型判断下一步”。医疗场景要可控。

09 多 Agent / LangGraph 多 Agent 为什么不直接一个大 Prompt 全做完？
口语化回答

一个大 Prompt 虽然简单，但不好控制，也不好定位问题。导诊里安全判断、信息采集、知识检索、报告解读、医生复核职责不同，拆成节点后每一步输入输出更清楚，哪个环节出错也更容易看。尤其医疗场景，危急症状要前置拦截，不能让模型生成完再补救。

相关知识点解释

拆分不是为了炫技，是为了可控、可观测、可兜底。

可能继续追问

如果问缺点：节点多会增加延迟和维护成本，所以要控制节点粒度。

不要这么答

不要说“多 Agent 效果一定比单 Agent 好”。

10 多 Agent / LangGraph 你说的症状问询状态机怎么实现？
口语化回答

我理解它就是按固定阶段收集信息，不是让用户随便聊。先收主诉，再看现病史，比如持续多久、是否伴随发热疼痛；再问既往史、过敏史、用药史。每个阶段都有必填字段，如果字段缺失，就生成补充追问；如果过程中出现胸痛、意识丧失这类高危信号，就中断普通问询，转急诊提示。

相关知识点解释

31 模型与评估 Recall@5 是怎么计算的？
