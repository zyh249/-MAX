项目边界

先把两个项目的关系说清，否则面试官会认为你在重复包装同一段经历。

推荐口径：RAG 是知识底座，多 Agent 是业务编排

医疗知识库 RAG 问答系统负责资料清洗、切分、召回、重排、引用来源、安全拒答，是一个知识问答底座；医疗导诊与报告解读多 Agent 系统负责把患者输入、问诊状态机、危急症状拦截、报告解读和医生复核串成业务流程，其中“医学指南 RAG Agent”只是调用知识底座的一类节点。

患者输入症状、报告、咨询问题
多 Agent 编排分诊路由、状态机追问、报告并行解读、HitL
RAG 知识底座FAQ、BM25、Milvus、Reranker、引用
安全兜底危急词、拒答、免责声明、人工复核
前端展示摘要、引用、风险提示、复核状态

技术点地图

每个点都按“作用、为什么选、类似技术、面试风险”整理。

LLM / Qwen

负责理解问题、生成追问、组织科普回答。

作用
把结构化上下文、检索片段和安全规则转成自然语言回答。
好处
中文能力较好，工程接入成熟，适合医疗科普类回答生成。
类似技术
DeepSeek、GLM、Baichuan、Llama、GPT 系列。
风险
不能说“模型诊断疾病”，只能说“辅助生成科普解释和就医建议”。

LangGraph

把多步骤 LLM 流程做成可控的状态图。

作用
定义节点、边、条件分支和共享 State，适合导诊这种有中断和回退的流程。
好处
比简单链式调用更可控，能表达状态机、路由、人工复核和异常分支。
类似技术
AutoGen、CrewAI、Semantic Kernel、Dify Workflow、Coze Workflow。
风险
要能说出 State 字段、节点职责和条件边，不要只说“用了多 Agent”。

LangChain

连接模型、Prompt、Retriever 和工具调用。

作用
封装检索、提示词、模型调用、输出解析等 RAG 基础链路。
好处
生态成熟，文档加载器、Retriever、PromptTemplate 等组件齐全。
类似技术
LlamaIndex、Haystack、RAGFlow、Dify。
风险
别把 LangChain 讲成业务核心，核心还是你的数据、召回、评测和安全策略。

多 Agent Workflow

多个专职节点协同处理一个业务流程。

作用
把分诊路由、症状问询、指南检索、报告解读、医生复核拆成职责清晰的节点。
好处
便于排查问题，也能把安全规则放在生成之前，降低不可控输出。
类似技术
普通工作流、规则引擎、BPMN、Dify/Coze 编排。
风险
一年经验不要说自己设计了整套架构，建议说“参与拆分，负责部分节点实现”。

问诊状态机

让多轮问询按固定阶段推进。

作用
按主诉、现病史、既往史、过敏史/用药史采集信息，缺字段时追问。
好处
比自由对话更稳定，能解释为什么追问、什么时候结束、何时中断。
类似技术
有限状态机、表单引擎、规则树、slot filling。
风险
要能说“缺失字段怎么判断”，不能只说“让模型自己追问”。

TypedDict + Pydantic

约束 Agent 节点间的数据结构。

作用
定义患者信息、症状、风险标记、科室建议、复核状态等字段。
好处
降低字典字段混乱和 LLM 输出格式不稳定带来的解析错误。
类似技术
dataclass、Marshmallow、JSON Schema、TypeScript interface。
风险
面试官会问必填字段、默认值、校验失败怎么办，要准备兜底逻辑。

RAG

让模型基于知识库回答，减少胡编。

作用
先检索疾病、药品、急救、科室 FAQ，再让模型基于片段生成回答。
好处
可溯源、可更新、比单纯微调更适合业务知识变化频繁的场景。
类似技术
微调、知识图谱问答、搜索引擎问答、Long Context。
风险
必须说清“不检索到证据就拒答或人工复核”，医疗场景不能硬编。

FAQ 快速命中

高频标准问题不用每次走完整 RAG。

作用
挂号科室、检查注意事项、常见药品用法等问题优先返回标准答案。
好处
快、稳定、成本低，适合可标准化的问题。
类似技术
意图分类、ES 关键词检索、规则模板、Redis 缓存。
风险
要说明 FAQ 命中不可靠时会回退到 RAG，而不是强行返回错答案。

BM25

关键词匹配强，适合药名、检查项、专有名词。

作用
按词频、逆文档频率和长度归一化进行文本召回。
好处
对精确词、药品名、指标名命中稳定，能补向量召回的短板。
类似技术
TF-IDF、Elasticsearch、OpenSearch、Lucene。
风险
不要说 BM25 理解语义，它主要解决关键词层面的召回。

BGE-M3 / Embedding

把文本转成向量，用语义相似度召回。

作用
用于疾病描述、用药咨询、科室推荐等自然语言问题的语义检索。
好处
BGE-M3 支持多语言、多粒度，也能提供稠密和稀疏表示思路。
类似技术
m3e、bge-large-zh、E5、text-embedding 系列。
风险
要能解释向量召回不等于最终答案，还要重排、引用和安全约束。

Milvus

存储向量并支持近似最近邻检索。

作用
保存知识块向量，按 query embedding 检索相似内容。
好处
适合大规模向量检索，支持索引、过滤、集合管理。
类似技术
FAISS、Qdrant、Weaviate、pgvector、Elasticsearch dense_vector。
风险
面试官可能问索引类型和过滤字段，不熟就说“项目中主要负责接入和参数调优”。

BGE-Reranker

对召回候选做精排，提高上下文质量。

作用
把 BM25 和向量召回的候选片段重新排序，选出更适合生成答案的上下文。
好处
Cross-Encoder 能同时看 query 和 passage，比单纯向量相似度判断更细。
类似技术
m3e-reranker、Cohere Rerank、ColBERT、LLM rerank。
风险
要说明重排会增加耗时，所以需要控制 rerank_k 和 P95。

父子分块

兼顾召回精度和生成上下文完整性。

作用
小块用于召回，大块用于给模型阅读，避免片段太碎造成理解缺失。
好处
比固定长度切分更能保留标题层级和医学资料上下文。
类似技术
递归分块、Markdown 标题切分、语义分块、滑动窗口。
风险
要能说清父块、子块分别存什么，引用展示用哪个粒度。

Hybrid Search

BM25 解决精确词，向量解决语义表达。

作用
合并关键词召回和向量召回，再用重排模型筛选上下文。
好处
药名、指标名、自然语言症状描述都能兼顾。
类似技术
RRF、加权融合、候选并集 + rerank、ES 混合检索。
风险
如果没做复杂公式，就说“候选合并后交给 reranker”，别装成算法专家。

安全 Prompt

约束模型只做科普，不做诊断。

作用
把用户问题、检索上下文、引用来源和医疗安全规则组装成提示词。
好处
统一输出风格，降低无来源回答、越界诊断、过度承诺。
类似技术
Guardrails、规则引擎、内容审核模型、函数调用约束。
风险
Prompt 不是唯一安全手段，必须配合规则前置、拒答和医生复核。

HitL 医生复核

医疗建议推送前需要人工确认。

作用
AI 输出先进入待复核状态，由医生确认或修正后再展示。
好处
降低医疗风险，符合“AI 辅助，不替代医生”的业务边界。
类似技术
审批流、人工审核队列、客服转人工、LangGraph interrupt。
风险
初级开发建议说“实现状态流转和页面提示”，别说自己定义了合规制度。

FastAPI

封装问答、检索、反馈和状态接口。

作用
对前端提供问答、检索结果、引用来源、风险提示、复核状态等接口。
好处
异步支持好，和 Pydantic 配合紧密，接口文档自动生成。
类似技术
Flask、Django REST Framework、Tornado、Sanic。
风险
要能讲接口字段、异常返回、日志记录，别只讲“搭了后端”。

Redis

缓存高频问答、会话状态或临时结果。

作用
用于 FAQ 缓存、会话上下文、热点数据或任务状态。
好处
读写快，适合降低重复查询和接口响应时间。
类似技术
Memcached、本地 LRU、数据库缓存表。
风险
要能说缓存失效策略，至少说“按业务更新或 TTL 清理”。

MySQL / PostgreSQL

保存结构化业务数据和元数据。

作用
存 FAQ、用户反馈、引用元信息、医生复核状态、评测记录。
好处
事务和结构化查询稳定，方便统计和审计。
类似技术
SQLite、MongoDB、Elasticsearch、ClickHouse。
风险
如果写 PostgreSQL，就准备说明是否用了 JSONB；如果没用，就不要主动展开。

React + TypeScript + Ant Design

展示问答结果、引用来源、风险提示和复核状态。

作用
实现患者问询页、报告解析结果、加载态、异常态、反馈入口。
好处
TS 约束字段，AntD 提供成熟表单和组件，适合业务后台类页面。
类似技术
Vue + Element Plus、Arco Design、Naive UI、Next.js。
风险
要能讲清楚“引用来源怎么展示、流式回答怎么处理、错误态怎么提示”。

PyMuPDF

解析 PDF 报告或资料文本。

作用
从 PDF 资料或体检报告中抽取文本、页码和基础布局信息。
好处
速度快，适合文本型 PDF 的工程解析。
类似技术
pdfplumber、pypdf、PaddleOCR、Tesseract OCR。
风险
扫描件需要 OCR，不能说 PyMuPDF 能解决所有 PDF 识别问题。

asyncio.gather

并行执行多个独立评审任务。

作用
血常规、肝功、血脂等指标可并行解读，减少串行等待。
好处
对 IO 型 LLM 调用和接口调用有明显收益。
类似技术
线程池、任务队列、Celery、并行 Agent 节点。
风险
要说明异常隔离和超时处理，避免一个节点失败拖垮整体。

Evaluation 指标

用小规模标注集证明调优方向。

作用
记录 Recall@5、引用命中率、拒答准确性、P95 耗时、bad case。
好处
比“感觉效果更好”更可信，也方便复盘具体问题。
类似技术
RAGAS、DeepEval、TruLens、人工标注评测表。
风险
必须说明是开发测试口径，不要包装成线上业务指标。

严厉追问答案库

按“面试官怎么追、推荐回答、不能这么答”准备。
高危 你这两个项目是不是同一个项目拆成两段写？

推荐回答不是简单拆分。RAG 问答系统更偏底座，重点是资料清洗、FAQ、混合召回、重排、引用和安全拒答；多 Agent 系统更偏业务编排，负责患者输入后的分诊路由、状态机追问、报告并行解读和医生复核。多 Agent 里的医学指南 RAG Agent 调用的是知识库能力。

不要说“两个项目都是我独立负责的完整医疗 AI 系统。”这会显得范围过大。
高危 你一年经验，怎么会负责这么多核心架构？

推荐回答我没有负责整体架构，架构和医疗安全边界是团队一起定的。我主要负责可落地的工程部分：状态结构、部分 Agent 节点、RAG 数据处理、接口封装、前端展示和 bad case 复盘。简历里我用“参与”和“负责”区分了范围，能展开讲的是自己亲手做过的链路。

不要说“整体架构都是我设计的。”面试官会直接追系统设计、合规和上线责任。
高危 LangGraph 的 State 具体怎么设计？

推荐回答State 不是只放聊天记录，而是放业务字段。比如 patient_info、chief_complaint、symptoms、history、allergy、medication、risk_flags、department_suggestion、report_abnormal_items、rag_context、review_status。节点只读写自己负责的字段，条件边根据 risk_flags、missing_fields、review_status 决定下一步。

追问准备如果校验失败，我会让节点返回固定错误结构或进入补充追问，而不是让后续节点解析不完整字段。

高危 追问覆盖率 88% 是怎么算的？

推荐回答这是开发测试口径，不是线上指标。我们用 50 条预问诊样例标注关键缺失字段，比如年龄、持续时间、伴随症状、既往史、过敏史。系统生成追问后，看是否覆盖这些标注缺失项，覆盖项数除以应追问项数，大约 88%。

不要说“线上用户满意度提升 88%。”这和简历指标完全不是一回事。
高危 危急症状 20 条命中 19 条，漏掉的那条为什么没命中？

推荐回答我会把它解释成规则表达覆盖问题。比如用户没有直接说“胸痛”，而是说“胸口像被压住、冒冷汗”，初版规则只覆盖了显式关键词，后来把近似表达、同义词和组合症状加入规则或交给风险分类节点复核。

关键点医疗安全场景里漏召比误召更严重，所以宁愿把疑似高危转人工，也不要让模型继续普通问询。

高危 你们的医生 HitL 是真有医生端，还是简历包装？

推荐回答我的口径是实现“待复核状态流转和展示”，不是说我负责完整医生工作台。AI 生成导诊建议、报告解读和摘要后，接口返回 review_status=pending，前端展示待复核，医生确认或修正后状态更新为 approved/revised。未经确认的内容只作为辅助草稿。

不要说“AI 输出直接给患者看，只是加免责声明。”医疗场景这样说会很危险。
高危 报告异常项一致率 90% 怎么评？参考范围怎么处理？

推荐回答这是对 20 份脱敏报告里 80+ 指标做人工抽检，主要看三点：异常项是否定位正确、参考范围是否解释正确、通俗解释是否越界诊断。参考范围会优先使用报告原文里的范围，不自己推断男女年龄差异；如果报告没有范围，只做谨慎解释并提示以医院报告和医生意见为准。

不要说“可以根据指标判断疾病。”应该说“提示关注异常项，不输出确诊结论”。
常问 并行节点耗时降低 70%，为什么能降这么多？

推荐回答因为部分报告指标或质控维度之间互不依赖，串行时每个 LLM/API 调用都要等待上一个完成；改成 asyncio.gather 后，总耗时更接近最慢的单个任务，而不是所有任务耗时相加。这个指标是测试样例口径，主要用于证明并行化方向有效。

补充并行也要加超时和异常隔离，否则一个任务失败会影响整体结果。

高危 RAG 的 Recall@5 怎么算？

推荐回答基于内部 120 条标注问答集，每个问题标注一个或多个可支持答案的知识片段。检索返回 Top5 后，只要 Top5 里包含任一标注支持片段，就记为召回成功。成功问题数除以总问题数就是 Recall@5。

不要说“召回率就是用户觉得回答对。”用户主观满意不是 Recall@5。
常问 答案引用命中率 68% 到 81% 是什么？

推荐回答它看的是生成答案里展示的引用来源是否真的支持回答，而不仅是检索到了相关片段。我们抽查答案对应引用，如果引用片段能覆盖核心结论，就算命中。提升主要来自父子分块、metadata 过滤和 reranker 调整。

关键点引用命中率比单纯召回更接近用户能看到的可追溯质量。

高危 你写 P95 不含模型生成，那整体耗时是多少？

推荐回答我会明确区分链路耗时和端到端耗时。简历里的 P95 指检索和重排链路，不含 LLM 生成，因为模型生成受模型服务、输出长度和流式返回影响很大。端到端用户感知会通过流式输出改善首字响应，但完整回答耗时要按实际模型服务统计。

不要说“整个大模型回答 1.8 秒稳定完成。”这很容易被追穿。
高危 BM25 和向量召回怎么融合？

推荐回答如果项目没有复杂算法，就不要硬讲公式。可以说开发阶段主要做候选集合并：BM25 取一批关键词候选，向量召回取一批语义候选，去重后带上来源和分数，再交给 BGE-Reranker 统一重排。这样比手工融合分数更容易解释和调试。

进阶如果被追 RRF，可以说明 RRF 是按排名做倒数融合，不依赖不同检索器分数尺度一致。

常问 top_k、rerank_k、score 阈值怎么定？

推荐回答不是拍脑袋，而是看 Recall、引用命中和 P95。top_k 太小会漏召，太大会增加重排耗时和噪声；rerank_k 要控制在重排模型能承受的范围内；score 阈值用于低置信度拒答或转人工。最终参数用 bad case 和小规模标注集迭代。

不要说“一般都设 5。”不同资料规模和模型延迟下没有固定答案。
常问 为什么选 BGE-M3，不选别的 embedding？

推荐回答主要考虑中文语义检索效果、社区成熟度和混合检索能力。BGE-M3 对多语言、多粒度和稠密/稀疏表示支持较好，适合医疗咨询这种既有短关键词又有长描述的问题。但我不会说它一定最好，模型选择需要结合数据集评测。

常问 为什么用 Milvus，不用 Elasticsearch 或 FAISS？

推荐回答Milvus 更偏向量数据库，适合管理向量集合、索引和向量召回；Elasticsearch 更强在关键词检索，FAISS 更像向量检索库，工程化的数据管理能力要自己补。项目里 Milvus 承担向量召回，BM25/FAQ 承担关键词和标准问答，两者职责不同。

常问 父子分块具体解决什么问题？

推荐回答医疗资料如果只按固定长度切，容易把适应症、禁忌、注意事项切散。子块小，方便精准召回；父块大，给模型足够上下文。引用可以展示子块命中的来源，同时生成时补充父块上下文，减少断章取义。

高危 医疗安全只靠 Prompt 吗？

推荐回答不靠单一 Prompt。Prompt 只是约束输出风格和边界，前面还有危急词硬规则、RAG 证据约束、低置信度拒答、人工复核状态。医疗场景要把安全规则前置，不能等模型生成后再补免责声明。

不要说“我写了一个强 Prompt，所以模型不会乱答。”这非常不可信。
基础 FastAPI 部分你具体做了什么？

推荐回答我会说自己封装过问答接口、检索结果结构、反馈记录接口，返回答案、引用、风险提示、耗时、review_status 等字段；同时处理异常状态，比如检索为空、模型超时、字段缺失，让前端能稳定展示。

基础 前端怎么体现 AI 应用能力？

推荐回答AI 应用前端不只是展示一段回答，还要展示引用来源、风险提示、加载状态、失败状态、医生复核状态和用户反馈。我的工作重点是把后端返回的结构化字段准确映射到页面，避免用户误把 AI 草稿当正式医疗意见。

常问 bad case 复盘具体怎么做？

推荐回答我会按问题类型记录：召回错、重排错、引用缺失、Prompt 越界、拒答不稳定、前端展示误导。每条记录包含 query、期望答案、召回片段、最终回答、问题原因和修改动作。这样下次调参不是凭感觉，而是围绕具体样例验证。

项目话术

控制在初级/一年经验能站得住的范围。

医疗知识库 RAG 问答系统怎么讲

这个项目更偏知识库问答底座。我主要做的是医疗资料清洗、元数据标注、父子分块，以及 FAQ 快速命中和 RAG 检索链路的接入调优。技术上用了 BM25 和 BGE-M3 向量召回做候选，再用 BGE-Reranker 重排，最后把引用来源、安全提示和免责声明一起返回给前端。评估上不是线上指标，而是用内部 120 条标注问答集看 Recall@5、引用命中率和拒答效果，通过 bad case 迭代分块、召回参数和 Prompt。

医疗导诊与报告解读多 Agent 系统怎么讲

这个项目更偏业务流程编排，RAG 只是其中一个知识增强节点。团队把流程拆成分诊路由、症状问询、医学指南 RAG、报告解读和医生复核几个节点。我主要参与节点输入输出、问诊状态结构、危急词前置规则、报告指标并行解读和复核状态流转。这个项目的重点不是让 AI 诊断，而是让 AI 辅助采集信息、整理摘要、提示风险，最后必须由医生确认。

个人定位一句话

我的定位不是大模型架构师，而是能把医疗 RAG 和 Agent Workflow 落到业务页面里的 AI 应用开发：我能做数据清洗、检索链路接入、状态结构、接口封装、前端展示和评测复盘，也知道医疗场景里 AI 必须有安全边界和人工兜底。

危险说法 为什么危险 替代表达
“整个医疗 Agent 架构都是我设计的。” 一年经验不合理，会被追问系统设计、合规、上线责任。 “团队确定整体方案，我负责部分节点实现、状态结构、接口联调和评测记录。”
“系统可以诊断疾病。” 医疗红线，AI 不能替代医生诊断。 “系统做科普解释、风险提示和接诊前摘要，正式意见需要医生复核。”
“效率提升 90%，准确率 95%。” 口径不清，像编数据。 “开发测试集中，某项指标从 A 提升到 B，样本量和评估方法是……”
“我靠 Prompt 控制模型不乱答。” 安全控制太单薄。 “Prompt 只是其中一层，还配合危急词规则、RAG 证据、拒答和人工复核。”
“Milvus 就是存文本的数据库。” 概念错误。 “Milvus 存向量和元数据，用于相似度召回；原文和业务元数据可存在关系库或对象存储。”
“Embedding 和 Reranker 差不多。” 说明检索链路没理解。 “Embedding 用于初召回，Reranker 对 query-passage 组合做更精细排序。”
